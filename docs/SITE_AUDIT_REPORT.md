# Аудит сайта «Клинический компас»

Дата: 21.10.2026. Проверена локальная копия проекта.

Аудит выполнен в изолированном окружении. Рабочая SQLite, MAX-токен и реальные сообщения не использовались. Публикация на сервер и отправка изменений в GitHub не выполнялись. Это технический отчёт о проверенном объёме, не заключение о клинической или юридической готовности продукта.

## 1. Подключённые инструменты и устройство проекта

- Next.js 15.5.28, React 19, TypeScript; статический экспорт. Кабинеты переключаются внутри `/`; отдельные маршруты: `/terms/`, `/privacy/`, `/consent/`, `/cookies/`, страница 404.
- FastAPI, SQLAlchemy, SQLite; авторизация через HttpOnly cookie. Клиент обращается к `/api/v1`; MAX использует отдельный обработчик и планировщик.
- Playwright Test и Chromium; Playwright MCP и Chrome DevTools MCP установлены локально и реально вызваны через MCP SDK. Конфигурация находится в `.codex/config.toml`; журнал — `clinical-compass/audit-results/mcp.json`. Для появления этих серверов в списке инструментов новой сессии нужно открыть этот проект с его конфигурацией.
- Vitest, Testing Library, jsdom; pytest для серверной логики; axe для автоматических проверок доступности; Lighthouse для собранного сайта.
- Сервер тестов: `scripts/audit_server.py`, порт 8011, отдельная база `tmp/browser-audit.db`. Интерфейс проверки: 3130. Статическая сборка для Lighthouse: 3131. Внешний транспорт MAX принудительно отключён в тестовом сервере.
- До правок сохранялась локальная копия исходного состояния (в репозиторий не входит). Секретные файлы и рабочая БД в эту копию не включались.

## 2. Проверенные страницы

24 экрана приложения:

- Вход.
- Врач: обзор, пациенты, уведомления, задания, сообщения, ИИ-помощник, база знаний, отчёты, настройки.
- Пациент: главная, история наблюдения, назначения, опросники, документы, профиль.
- Администратор: обзор системы, Backend и API, проверка функций, данные и показатели, библиотека опросников, учётные записи, журнал аудита, настройки.

Дополнительно проверены четыре правовые страницы. Автоматический обход экранов выполнен при ширинах 320, 375, 390, 768, 1024, 1440 и 1920 px. Снимки основных экранов сохранены для 320, 390 и 1440 px, правовых страниц — для 320 px: `clinical-compass/audit-results/screenshots/`.

## 3. Протестированные сценарии

- Ошибка входа, переключение видимости пароля, вход в три роли, выход с удалением серверной cookie.
- Вход по логину, почте и телефону — серверные тесты.
- Создание врача администратором с подтверждением; ограничения редактирования врачебного профиля.
- Создание задания, изменение статуса и сохранение после перезагрузки.
- Получение пациентом одноразового кода MAX; проверка срока 24 часа и регистрозависимого хэша на сервере.
- Запрет пациенту обращаться к административным/врачебным API; запрет другому врачу изменять чужую задачу или читать чужой аудит.
- Ответ врача пациенту через подменённый транспорт MAX, чтение переписки; реальная отправка не выполнялась.
- Числовые ответы опросников, отсутствие бессмысленного суммарного балла у дневника, перенос просроченного повторного назначения в будущее.
- Блокировка сбора ответов после остановки бота/отказа от согласия.
- Недоступный API в кабинете пациента: понятная ошибка и повтор загрузки вместо начальных образцов данных.
- Очистка поиска, Escape и восстановление прокрутки модального окна.

## 4. Обнаруженные ошибки

1. Тесты могли обращаться к рабочей БД.
2. Выход очищал только клиентское состояние; серверная cookie оставалась.
3. Восстановление входа доверяло сохранённой в браузере роли без проверки текущей учётной записи.
4. Изменение заданий и ИИ-материалов не проверяло закрепление пациента за врачом; журнал аудита не был ограничен своими сущностями.
5. При первом создании БД ежедневные назначения могли отсутствовать из-за незафиксированных в сессии версий опросников.
6. Повторное начальное заполнение могло восстановить отменённое ежедневное назначение.
7. После отказа/остановки бота обработчик мог продолжать принимать данные.
8. Некорректные типы ответов, NaN и Infinity принимались или приводили к исключению; ошибки валидации API отображались нечитаемо.
9. У дневника суммировались несопоставимые показатели без явно заданного правила расчёта.
10. Просроченная повторяющаяся анкета могла назначаться снова на уже прошедшую дату.
11. При смене диалога поздний ответ API мог подставить сообщения другого пациента; черновик не был разделён между диалогами.
12. В ряде мест использовалась фиксированная дата октября; календарь сравнивал только число месяца.
13. Пациенту в разделе опросников показывались врачебные задачи вместо назначенных анкет.
14. При сбое API кабинеты могли отображать начальные образцы данных.
15. Админская «полная проверка» была таймером и показывала успех без проверки сервера; некоторые проценты были константами.
16. Переполнение обзора, KPI, заголовков, адресов API и правовых страниц на узких экранах; недостаточный контраст подвала, некорректная ARIA-разметка правовой таблицы, пропуски уровней заголовков и отсутствие main на входе.
17. Страница входа загружала код кабинетов и графиков до авторизации; шрифт запрашивался с Google.

## 5. Что исправлено

Для перечисленных ошибок внесены локальные исправления: изолированные тестовые БД; серверный выход; проверка учётной записи; ограничение доступа к сущностям и аудиту; корректное первичное назначение и сохранение отмены; блокировка остановленных привязок; валидация ответов и понятные сообщения об ошибках; явный режим подсчёта балла; пропуск просроченных повторов; разделение черновиков и защита от поздних ответов переписки; обновление сообщений с очисткой таймера; актуальные даты; правильный источник анкет пациента; состояния ошибок загрузки; реальная проверка FastAPI/SQLite вместо таймера.

При отправке врачу/пациенту проверяются актуальные согласия. Не создавалось обхода согласия. Существующий механизм юридических документов требует отдельной проверки реквизитов клиники перед реальным использованием.

Код рабочих кабинетов вынесен в отдельные загружаемые модули. First Load JS страницы входа уменьшился с 303 до 165 КБ (примерно на 46%). Сохранены функции и внешний вид, включая текущую сине-белую палитру и композицию входа.

## 6. Изменения стилей

- Сохранены Manrope, карточки, основные размеры и цвета; шрифт теперь поставляется локально через пакет Fontsource.
- Уточнены минимальные размеры дочерних элементов сетки и перенос длинных строк.
- Общий вторичный цвет текста стал контрастнее; улучшена семантика заголовков входа.
- Не выполнялась полная перепись CSS. Старые повторяющиеся правила остаются техническим долгом; замена всей системы стилей увеличила бы риск регрессий.

## 7. Адаптивность

Исправлены растягивание обзора врача, двухколоночные KPI на самых узких экранах, кнопки заголовков админки, строки анкет пациента, длинные адреса API и длинные заголовки правовых страниц. Проверка измеряет ширину документа и падает при переполнении, а не скрывает его через глобальный overflow:hidden.

В таблицах с большим количеством колонок сохраняется локальная прокрутка контейнера. Это не переполнение всей страницы. На реальных мобильных устройствах жесты и экранную клавиатуру отдельно не проверяли.

## 9. Автоматические проверки

- pytest: 23 теста прошли. Остаётся предупреждение Starlette о будущем переходе тестового клиента с httpx.
- Vitest: 9 тестов прошли, включая проверки компонентов и ошибок API.
- Playwright: 7 тестов прошли в финальном общем прогоне, включая 168 проверок ширины (24 экрана × 7 размеров), основные сценарии и четыре правовых маршрута. Журнал: `clinical-compass/audit-results/e2e.log`.
- TypeScript и ESLint: без ошибок.
- Production build: успешен.
- Автоматический axe запускался для входа, сообщений врача, профиля пациента и учётных записей администратора; дополнительно — страницы конфиденциальности. Это выборочная проверка, не сертификация WCAG всего продукта.
- В проверенном обходе нет необработанных ошибок JavaScript и ответов сервера 5xx. Намеренный ответ 503 проверен отдельным тестом обработки ошибок.

Артефакты содержат вымышленные тестовые аккаунты; не подключать тесты к рабочей БД.

## 10. Оставшиеся ошибки и ограничения

- Экспорт PDF в разделе отчётов пока не реализован; кнопка сообщает об этом. Автоматическая генерация полноценного медицинского отчёта не добавлялась в рамках минимального исправления ошибок.
- ИИ-помощник формирует локальные шаблонные черновики, внешняя модель не подключена. Некоторые иллюстративные графики/события и прежние справочные экраны требуют привязки к фактическим данным; их нельзя считать полноценной аналитикой.
- В npm audit остаётся цепочка braces → micromatch → fast-glob → ESLint Next (5 записей high, одна цепочка зависимости). Автоматическое предложение npm — понижение несовместимой версии ESLint Next; оно не применено. Зависимости compression и postcss обновлены совместимыми overrides, число записей снизилось с 9 до 5. Следить за upstream-исправлением; не принимать непроверенные шаблоны glob из внешнего ввода.
- В коде есть development-настройки JWT/cookie и начальные учётные записи. Перед публичным размещением необходимы отдельная конфигурация секретов, HTTPS, защита от перебора и проверка начальных аккаунтов. Секреты окружения аудит не раскрывал и не заменял.
- Юридические страницы содержат незаполненные реквизиты оператора. Правомерность обработки медицинских данных и текст согласий этим техническим аудитом не подтверждаются.
- Единая политика часовых поясов всех дат API и переходов времени требует отдельного сквозного теста: часть данных сериализуется без явного UTC-смещения.
- Нет подтверждения доставки реальных сообщений MAX, обработки сбоев внешнего сервиса, длительной работы планировщика и восстановления после отключения сети.

## 11. Что не проверено

Production-домен и публичная инфраструктура; реальные MAX webhook/polling и уведомления; Safari/Firefox/реальные телефоны; нагрузка, длительные утечки памяти, восстановление резервной копии рабочей БД; все сочетания клинических правил и валидность медицинских шкал; юридическое соответствие. Не выполнялись реальные действия от имени пациентов, отправка сообщений или автоматическая публикация.

## 12. Рекомендации

1. Провести отдельный приёмочный сценарий с вымышленным пациентом и тестовым MAX-чатом: привязка → актуальное согласие → назначение → ответы → сигнал лечащему врачу → ответ врача → отмена согласия.
2. Перед публикацией заполнить реквизиты клиники, утвердить документы, защитить production-конфигурацию и убрать начальные аккаунты.
3. Реализовать экспорт отчётов и заменить оставшиеся иллюстративные блоки фактической аналитикой.
4. Добавить CI с pytest, Vitest, Playwright и сборкой. Периодически обновлять зависимости и прогонять регрессии.
5. Провести длительный тест планировщика, повторной доставки и восстановления; затем проверку на реальном мобильном устройстве.

Обновлённый сайт использует файлы локального проекта. Уже запущенные обычные серверы могут продолжать выполнять старый Python-код до перезапуска. Рабочий запуск и бот в ходе аудита не перезапускались.
